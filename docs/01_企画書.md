# 01. 企画書（起案）

## 1. 背景と課題

機械製図の授業・実習では、投影図から**断面図**を作図する演習が繰り返し行われる。
しかし現状の紙ベースの演習には次の課題がある。

| # | 課題 | 具体的な状況 |
|---|---|---|
| C-1 | **フィードバックが遅い** | 提出 → 教員が採点 → 返却まで数日。生徒は「どこが違ったか」を忘れた頃に結果を受け取る |
| C-2 | **採点負荷が高い** | 1 クラス 40 名 × 複数問。ハッチングの向き・切断してはいけない部品など、細かい確認が教員の手作業 |
| C-3 | **反復量が確保できない** | 方眼紙の準備・作図に時間がかかり、1 コマで解ける問題数が限られる |
| C-4 | **つまずきが可視化されない** | 「リブを切断してしまう」「かくれ線を残す」など典型的な誤りが、個人／クラス単位で集計されていない |
| C-5 | **自習しにくい** | 家庭学習では正解を照合できず、間違えたまま覚えてしまう |

断面図は「切り口にハッチングを施す」「リブ・アーム・軸などは長手方向に切断しない」といった
**ルールの理解**が問われる分野であり、**即時フィードバック付きの反復練習**との相性が非常に良い。

## 2. 目的

> **投影図から断面図を作図する力を、即時採点付きの反復演習で定着させる。**

副次目的:

- 教員の採点負荷を下げ、指導（つまずきへの介入）に時間を回す
- クラス全体の誤答傾向を可視化し、授業の重点を決める材料にする

## 3. ターゲットユーザー

| ペルソナ | 想定 | 主な使い方 |
|---|---|---|
| **生徒**（主）| 工業高校・高専・職業訓練校の製図履修者、機械設計技術者試験の受験者 | 授業中の演習、宿題、試験前の反復 |
| **教員**（副）| 製図担当教員 | 問題の追加、クラスの進捗・誤答傾向の確認 |
| **独学者** | 資格取得を目指す社会人 | 自習ドリル |

利用端末は**学校配備の Chromebook / iPad / PC** を想定。タッチ操作必須。

## 4. 提供価値（このアプリでしかできないこと）

1. **描いた瞬間に採点される** — 提出ボタンを押すと 1 秒以内に正誤・部分点・誤り箇所のハイライトが返る
2. **誤りに「理由」が付く** — 「リブは長手方向に切断してもハッチングしません（JIS B 0001）」のように、ルール名付きで指摘する
3. **方眼紙が不要** — 教科書と同じ方眼グリッド上で、クリック／タップだけで作図できる
4. **教員が問題を足せる** — スプレッドシートに 1 行足すか、付属の作問ツールで正解を描くだけで問題が増える（コード変更不要）

## 5. 成功指標（KPI）

| 指標 | 目標（導入 1 学期後） |
|---|---|
| 1 人あたりの演習問題数 | 紙演習比 **3 倍以上** |
| 同一分類問題の 2 回目正答率 | 1 回目比 **+25pt 以上** |
| 教員の採点時間 | **80% 削減**（自動採点分） |
| 典型誤答（リブ切断・かくれ線残し）の発生率 | 単元終了時に **10% 未満** |

## 6. スコープ

### 対象に含む

- 断面図の**作図**演習（切り口の形状 ＋ ハッチング）
- 断面図の種類の識別・用語に関する**知識問題**（補助的に）
- 自動採点、解説表示、学習履歴
- 教員向けの問題登録と成績閲覧

### 対象に含まない（今回は作らない）

- 汎用 CAD 機能（自由曲線、寸法記入、公差、幾何公差）
- 3D モデルからの断面生成
- 投影図そのものを描く演習（第三角法の課題）→ 将来の別モードとして検討
- 成績管理システム（校務システム）との連携

## 7. なぜ Google Apps Script か

### 採用理由

| 観点 | 理由 |
|---|---|
| 導入コスト | 学校で既に Google Workspace for Education を使っている場合、**サーバも認証も追加費用ゼロ** |
| 認証 | 学校ドメイン限定公開が設定 1 つで済む。`Session.getActiveUser().getEmail()` で本人特定できる |
| データ管理 | 問題・成績が**スプレッドシート**なので、教員が中身を直接見て編集できる。エクスポートも容易 |
| 運用 | サーバ保守・証明書更新・バックアップが不要 |
| 配布 | URL を配るだけ。インストール不要、Chromebook でそのまま動く |

### 受け入れる制約（詳細は [03_設計方針](03_設計方針.md#7-gas-固有の制約と対策)）

- 画面は `HtmlService` の iframe サンドボックス内で動く（外部 JS の読み込みに制限あり）
- サーバ呼び出しは `google.script.run` の**非同期のみ**、引数・戻り値は JSON 化可能な型に限る
- 1 実行あたり最大 6 分、スプレッドシート書き込みは同時実行に弱い（`LockService` で排他）
- スプレッドシートは大量レコードに弱い（数万行規模でローテーションが必要）

→ いずれも「1 クラス〜1 学年規模の演習アプリ」であれば実用範囲内と判断。

## 8. 想定リスク

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| R-1 | 作図 UI が難しく、生徒が「操作」でつまずく | 学習効果が出ない | **グリッドのセルを塗る方式**にして操作を単純化。斜面は三角セルで表現（[04](04_データモデルと採点.md) 参照） |
| R-2 | 問題データの作成コストが高い | 問題数が増えない | Phase 3 で**作問ツール**（教員が同じ UI で正解を描いて JSON 出力）を用意 |
| R-3 | 採点が厳しすぎ／甘すぎる | 生徒の信頼を失う | 部分点（Jaccard 係数）＋ 明示的な許容ルール。判定結果を教員が上書きできる余地を残す |
| R-4 | 同時アクセス（1 クラス 40 名同時提出）で書き込み競合 | 記録欠損 | `LockService` ＋ 追記のみ設計。記録失敗時もクライアント側の採点結果は表示する |
| R-5 | 個人メールアドレスの取り扱い | 個人情報管理 | 匿名モード（出席番号入力）を用意し、既定は学校ドメイン内限定公開とする |
| R-6 | 教科書の図をそのまま取り込むと著作権に触れる | 公開できない | 問題図は**すべて自作のベクタデータ**として作成する（教科書の図は参考にとどめる） |
